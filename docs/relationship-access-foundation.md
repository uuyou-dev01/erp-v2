# 账号、关系与数据权限底层规则

最后更新：2026-09-09

这份文件是邀请、登录、外部协作、企业连接和货盘共享的产品与实现基线。新增角色、页面或权限时，先判断属于哪一种关系，不得用“朋友”“合作方”之类的称呼替代数据关系。

## 一、五个不能混用的概念

| 概念                                   | 回答的问题                                 | 是否自动获得对方数据           |
| -------------------------------------- | ------------------------------------------ | ------------------------------ |
| `User`                                 | 这个登录的人是谁                           | 否                             |
| `Membership`                           | 这个人是否属于某个企业、在企业内是什么角色 | 仅获得成员角色明示的企业内权限 |
| `LocationFulfiller`                    | 这个人是否受托处理某个仓库范围内的任务     | 仅获得该范围的任务能力         |
| `OrganizationConnection`               | 两个企业是否互相确认了真实经营主体         | 否                             |
| `OfferVisibility` / `ServiceAgreement` | 哪项业务数据或服务明确开放给谁             | 仅在规则有效期和范围内开放     |

同一个 `User` 可以同时拥有多种关系。例如：既是 A 企业某个范围的外部任务负责人，又是 B 企业的所有者。两种身份共用一个账号，但数据、导航和权限不合并。

## 二、邀请与账号规则

1. 任务邀请只创建一条待接受的 `LocationFulfiller`，不会预先创建可登录账号；当前实现按仓库划分协作范围。
2. 被邀请邮箱没有账号时，可从邀请页注册个人账号。注册只建立 `User`；点击“接受”后才把该账号绑定到任务协作关系。
3. 接受任务邀请不会创建 `Membership`，不会让被邀请人加入邀请方企业。
4. 被邀请邮箱已有账号时，必须使用相同邮箱登录后接受。
5. 邀请页必须提前说明任务范围、角色、可见范围和“不加入企业”的边界。
6. 邮箱验证属于身份可信度层，不能改变上述关系和授权语义；完成邮箱投递前，公网自助注册继续默认关闭。

## 三、外部任务角色

| 角色                  | 能看什么                                                         | 能做什么                                       | 不能做什么                           |
| --------------------- | ---------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------ |
| 任务负责人 `MANAGER`  | 当前范围待处理与已分派任务、任务状态；未成为执行人前不显示敏感信息 | 领取执行、指派给协作者、转派、撤回到待处理队列 | 查看采购成本、其他仓库库存、企业设置 |
| 任务协作者 `OPERATOR` | 分派给自己或可领取的当前范围任务；成为当前执行人后显示必要信息     | 领取并完成任务类型要求的具体操作               | 指派他人、查看未授权企业数据         |

保留旧 `BACKUP` 数据的读取兼容，新的邀请只允许任务负责人或任务协作者。

任务卡片必须显示具体类型，例如“订单发货”；关系名称、导航和空态不得把整个合作关系固定成某一种任务。客户姓名、电话和地址遵循最小可见原则：只有当前执行人可见。负责人需要亲自执行时必须先领取任务。

## 四、关系生命周期

任务协作状态固定为：

`INVITED → ACTIVE → SUSPENDED → ACTIVE`，或从有效状态进入 `ENDED`。

- `SUSPENDED`：临时停用，可恢复，不接收新任务。
- `ENDED`：长期关系结束，不可直接当作暂停展示；重新合作应留下新的 `REOPENED` 事件。
- 暂停或结束时，协作者已领取但未完成的任务必须退回待处理队列，历史工作记录保留。
- 每次邀请、接受、角色变化、暂停、恢复和结束都写入追加式 `LocationFulfillerEvent`，不得覆盖历史。

## 五、登录后的去向

| 当前账号状态     | 默认入口                                           |
| ---------------- | -------------------------------------------------- |
| 仅有任务协作关系 | `/collaboration` 个人协作中心                      |
| 有企业成员身份   | `/workbench` 所选企业 ERP                          |
| 两者都有         | 默认进入 ERP，可通过“任务协作”随时切回个人协作中心 |
| 两者都没有       | `/onboarding`                                      |

邀请链接和用户主动访问的 `/collaboration` 路径优先保留，不被默认 ERP 跳转覆盖。

个人协作中心必须回答三件事：正在与谁协作、之后的任务去哪里、未来是否需要建立自己的 ERP。空任务页不能是死胡同，必须保留“合作关系、我的任务、个人账号、创建自己的企业”的导航。

## 六、长期发展路径

外部协作者有两条同等合法的路径：

1. 只参与任务协作：长期保留个人账号和任务关系，新任务持续进入个人协作中心，不要求建立 ERP。
2. 开始经营自己的生意：同一账号创建自己的 `Organization`、店铺和独立库存，再向邀请方申请企业连接。

创建自己的企业不会复制、继承或共享邀请方库存。库存永远属于创建它的经营主体。

## 七、企业连接与业务授权

企业连接只确认“我们知道对方是哪家企业”，不是数据授权。

建立连接后，双方仍然默认看不到对方的：

- 全量库存与库位；
- 采购成本和利润；
- 客户订单与资金；
- 其他仓库或其他合作方。

要开展业务，必须再创建明确授权：例如向指定连接企业发布货盘，或签订限定范围的服务协议。定向货盘直接指向对端 `Organization` 和有效 `OrganizationConnection`，不要求先创建联系人 `Partner` 档案。

连接解除后，依赖该连接的未来数据访问立即失效；历史成交、工作记录和审计事件继续保留。不可用详情统一返回不泄露资源是否存在的 404 页面。

## 八、产品复杂度约束

1. 不建设通用“权限积木”或给普通用户暴露几十个权限开关。
2. 权限来自少量稳定角色、关系状态和明确业务授权。
3. 关系层使用稳定业务语言：任务负责人、任务协作者、企业连接、指定企业可见；具体卡片再显示订单发货、信息确认、盘点等任务类型。
4. 新增跨主体能力时先选择已有关系；确实无法表达时才新增关系类型。
5. 身份确认、业务授权、资源所有权和任务执行必须分别校验，不能用单个“合作中”状态代替。

## 九、实现不变量

- `LocationFulfiller` 不能推导出 `Membership`。
- `OrganizationConnection` 不能推导出 `OfferVisibility` 或库存权限。
- `OfferVisibility.viewerOrganizationId` 必须来自当前有效连接；读取时也必须再次校验连接仍有效。
- 外部任务查询必须同时校验用户、关系状态、仓库范围和角色能力。
- 客户地址只返回给当前任务执行人。
- 暂停、结束、连接解除必须有撤权测试。
- 每条关键链路既要有数据库断言，也要有真实浏览器截图证据。

## 十、变更验收清单

任何涉及本链路的变更至少验证：未注册邀请、已有账号接受、个人协作空态、新任务出现、任务负责人指派、任务协作者执行、创建自己的企业、企业连接、显式货盘共享、连接解除撤权，以及跨企业成本/库存不可见。
