# 账号与企业体系后续实施文档

> 文档日期：2026-08-15  
> 用途：只描述账号、认证、企业成员与企业连接模块自身尚未完成的工作。跨业务模块的改造请使用独立文档 `account-organization-module-integration.md`。

## 1. 当前基线

当前内部测试版已经具备：

- 账号注册、登录、退出和签名 Cookie 会话。
- 无企业账号进入 onboarding，而不是进入 ERP 工作台。
- 创建企业、默认店铺、所有者成员身份和默认访问权限。
- 一次性团队邀请链接，包含邮箱、角色、店铺范围、过期、撤销和重新生成。
- 多企业成员身份、活动企业切换、成员停用、主动退出和所有权转移。
- 企业协作码、合作方档案以及双方确认的企业连接。
- 个人资料和登录密码修改。

当前版本只适用于可信内部测试人员。邮箱未验证，邀请链接由管理员手工复制，不应直接作为公网生产认证方案。

## 2. P0：扩大测试范围前应完成

### 2.1 完整回收停用成员权限

现状：`deactivateTeamMember()` 会停用 `Membership` 并删除 `StoreAccess`，但数据库的兼容触发器只负责由 `StoreAccess` 创建或更新派生权限，不负责在删除时同步回收。因此以下记录可能残留：

- `InventoryPoolAccess`
- `ChannelAccess`
- `LocationAccess`

实施要求：

1. 在同一事务内停用成员并删除当前企业范围内的四类 Access。
2. 不能删除该账号在其他企业中的有效权限。
3. 明确跨企业仓储服务授权的归属；属于协议授权的权限不能仅凭店铺范围误删。
4. 增加“停用后使用另一个企业身份访问旧对象”的越权回归测试。

验收：停用成员不能继续访问原企业的店铺、库存池、渠道、仓库、任务和财务数据。

### 2.2 移除旧的管理员代建账号入口

现状：`app/actions/team.ts` 仍保留未被当前 UI 使用的 `createTeamMember()` / `createTeamMemberAction()`。该旧动作会给现有邮箱重置密码，与“个人账号归个人、通过邀请加入企业”的新模型冲突。

实施要求：

- 删除旧动作，或改为只创建 `OrganizationInvitation`。
- 禁止企业管理员直接覆盖已有用户姓名、密码、全局 `User.role` 和 `User.storeId`。
- 增加静态测试，确保团队 UI 和公开 Server Action 都无法走旧流程。

### 2.3 明确生产环境的受邀注册策略

现状：生产默认关闭自助注册。若受邀邮箱尚无账号，关闭注册后也无法通过邀请创建账号。

建议方案：

- 普通 `/register` 继续由 `AUTH_SELF_SIGNUP_ENABLED` 控制。
- 有效团队邀请令牌可以开放“仅限邀请邮箱”的注册。
- 注册完成后返回原邀请页，并继续要求验证邮箱后才能接受生产邀请。
- 邀请令牌不能被用来注册其他邮箱。

### 2.4 配置和内部测试后门收口

`requireAuthenticatedUser()` 当前允许使用 `ERP_DEV_USER_EMAIL` 作为开发兜底。生产化前需要：

- 生产启动时若配置 `ERP_DEV_USER_EMAIL`，直接拒绝启动或忽略并报警。
- 在环境配置文档中区分开发、测试、预发布和生产值。
- CI 增加生产配置安全检查。

## 3. P1：邮箱与会话生产化

### 3.1 数据模型

给 `User` 增加：

- `emailVerifiedAt DateTime?`
- `sessionVersion Int @default(1)`
- 可选的账号状态字段，例如 `ACTIVE / SUSPENDED / CLOSED`

新增通用 `AuthToken`：

- `userId`
- `type`: `VERIFY_EMAIL / RESET_PASSWORD / CHANGE_EMAIL`
- `tokenHash`
- `expiresAt`
- `consumedAt`
- `createdAt`

只保存令牌哈希，不保存原文。类型、用户和消费状态需要建立查询索引。

### 3.2 邮箱验证

流程：

1. 注册后创建验证令牌并发送邮件。
2. 未验证用户可以登录验证页、退出以及重新发送验证邮件。
3. 未验证用户不能进入 ERP 工作台，也不能接受生产团队邀请。
4. 验证令牌只能使用一次，过期后只能重新生成。
5. 重发时废弃同类型旧令牌并进行限频。

不要把供应商联系邮箱当成用户邮箱，也不要根据邮箱自动绑定 `Partner`、`User` 或 `Organization`。

### 3.3 密码找回与会话失效

新增页面：

- `/forgot-password`
- `/reset-password/[token]`

要求：

- 找回接口无论邮箱是否存在都返回相同文案和近似耗时。
- 重置成功后递增 `sessionVersion`。
- 会话载荷改为稳定的 `userId + sessionVersion + expiresAt`，不要继续以邮箱作为唯一会话主体。
- 修改密码、修改邮箱、管理员冻结账号后是否注销全部设备需形成统一策略。

当前 `changeMyPasswordAction()` 只更新密码哈希，不会让旧 Cookie 失效，生产化时必须一并处理。

### 3.4 SMTP 与邮件投递

环境变量：

- `APP_BASE_URL`
- `SMTP_HOST`
- `SMTP_PORT`
- `SMTP_SECURE`
- `SMTP_USER`
- `SMTP_PASSWORD`
- `MAIL_FROM`

邮件类型：

- 注册邮箱验证
- 团队邀请
- 企业连接请求与处理结果
- 密码重置
- 邮箱变更确认

邮件发送应通过 outbox/队列异步处理。动作成功只代表业务记录创建成功；投递状态必须单独记录为 `PENDING / DELIVERED / RETRY / FAILED`，失败可重试且不能伪装成已发送。

### 3.5 内部账号迁移

上线顺序：

1. 导出内部账号、成员身份和待处理邀请。
2. 修正临时、拼写错误或共用邮箱。
3. 部署新增字段和令牌表，暂不强制验证。
4. 开启新注册验证。
5. 现有账号下次登录进入补验证页。
6. 已接受成员关系继续有效；未接受邀请在消费前要求验证。
7. 不批量把全部历史邮箱标记为已验证。

## 4. P1：成员与权限生命周期完善

### 4.1 成员编辑

当前团队页能邀请和停用，但不能完整编辑现有成员。需要增加：

- 修改成员角色。
- 增减店铺范围。
- 查看并管理库存池、渠道、仓库的显式授权。
- 恢复已停用成员。
- 显示权限来源：店铺派生、协议授权或人工显式授权。

权限修改必须在事务内更新 `Membership` 与各类 Access，不能只修改列表显示使用的 `StoreAccess`。

### 4.2 所有者不变量

当前所有权转移由事务交换角色，但不变量主要依赖应用层。后续需要：

- 明确每个企业只能有一个有效 `OWNER`。
- 通过数据库约束、事务锁或可证明的串行化方案避免并发双所有者。
- 所有权转移记录操作者、旧所有者、新所有者和时间。
- 转移时同步该企业范围内的派生权限角色，但不要覆盖目标用户在其他企业中的角色。

### 4.3 弱化历史字段

`User.role` 和 `User.storeId` 目前仍用于兼容旧代码。长期权限来源应为：

- 企业角色：`Membership`
- 店铺权限：`StoreAccess`
- 库存权限：`InventoryPoolAccess`
- 渠道权限：`ChannelAccess`
- 仓库权限：`LocationAccess`

完成所有调用方迁移后，再停止写入或删除 `User.role`、`User.storeId`。迁移期间不得把这两个字段作为跨企业授权依据。

### 4.4 无企业用户的个人安全页

当前个人资料与修改密码动作依赖 `requireUserContext()`，尚未加入企业的账号只能访问 onboarding。后续应决定：

- 允许无企业用户进入独立账号设置页，并改用 `requireAuthenticatedUser()`；或
- 在 onboarding 内提供姓名和密码修改入口。

## 5. P1：企业资料与连接生命周期

### 5.1 企业资料

给 `Organization` 增加并提供设置 UI：

- 法定名称
- 工商注册号
- 联系邮箱和电话
- 国家或地区
- 地址和税务信息（若财务模块需要）

工商注册号只用于资料、合同和结算抬头，不能作为登录标识、加入凭证或权限凭证。敏感字段修改需要审计。

### 5.2 企业连接历史

当前同一企业对复用一条 `OrganizationConnection`，重新发起会覆盖前一轮的请求/响应信息；解除连接还会覆盖 `respondedById`，无法同时保留接受人和解除人。

建议增加不可变事件表 `OrganizationConnectionEvent`，记录：

- `REQUESTED`
- `ACCEPTED`
- `REJECTED`
- `ENDED`
- `REOPENED`

连接主表保留当前状态，事件表保留每次操作者、时间和原因。业务历史不随重新连接丢失。

### 5.3 一个企业对应多个合作方档案

当前连接主表每个企业对只有一条记录，并且只有一个 `initiatingPartnerId`。需要确认未来是否支持：

- 同一目标企业在多个本企业店铺各有一个 `Partner` 档案。
- 一个企业同时扮演供应商、代卖方、代发方等多个角色。

若支持，建议增加连接与 Partner 的关联表，而不是继续在连接主表保存单个 Partner。

## 6. P2：安全、审计和运营能力

### 6.1 审计

认证与企业模块至少记录：

- 登录成功/失败、退出和会话失效
- 注册、验证、重置密码、修改邮箱
- 邀请创建、重生成、撤销、接受和过期
- 成员角色、状态和范围变更
- 企业创建、资料变更、所有权转移
- 企业连接请求、接受、拒绝和解除

不得在审计、日志、监控、错误信息中记录原始密码、会话 Cookie 或邀请/认证令牌。

### 6.2 限频与风控

为登录、注册、验证重发、密码找回、团队邀请、协作码查询和企业连接分别配置限频。建议同时考虑：

- IP
- 邮箱或用户 ID
- 企业 ID
- 邀请或连接目标

协作码只能精确匹配，但仍需防止批量枚举。

### 6.3 设备会话、MFA 与 SSO

这些不是首个生产版本的阻塞项，可在完成邮箱与会话生产化后按风险实施：

- 设备会话列表和单设备退出
- MFA
- 企业 SSO/SAML/OIDC
- 异常登录提醒

## 7. 测试清单

后续每批实现至少覆盖：

- 未验证、已验证、冻结账号的登录矩阵。
- 邀请注册与普通注册开关组合。
- 验证、重置、邀请令牌的一次性、过期、撤销和并发消费。
- 密码重置及安全事件后的旧会话失效。
- 成员停用、退出、恢复、角色变更后的全部对象权限。
- 两个企业并发切换时 Cookie 与缓存不串租户。
- 并发所有权转移仍只有一个有效所有者。
- 企业连接多次请求、拒绝、解除、重连的完整历史。
- 邮件投递失败、重试和最终失败状态。

## 8. 完成定义

账号与企业模块达到生产可用，至少需要同时满足：

1. 生产不依赖开发账号兜底和未验证邮箱。
2. 所有认证令牌哈希存储、一次消费且有限期。
3. 密码和账号安全事件可以可靠注销旧会话。
4. 成员停用会回收所有本企业权限。
5. 所有权和连接历史可审计。
6. 生产关闭开放注册时，受邀新用户仍有安全注册路径。
7. 关键流程具备应用测试、数据库约束测试和浏览器端到端测试。
