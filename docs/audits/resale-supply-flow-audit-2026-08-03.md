# 货盘与倒买倒卖全流程审计

> 审计日期：2026-08-03
> 审计范围：采购、质检、转运、库存、货盘、代卖、成交、发货与分账
> 用户视角：做小规模倒买倒卖生意、不了解专业电商术语的普通经营者

> **本次规则澄清：**“按纯利润分成”只是两个测试案例中的具体约定，不是产品应内置的唯一标准。佣金、分成、固定服务费、运费、税费及其他费用由谁承担、是否参与分成、采用固定金额还是比例，均应以双方确认的协议为准。系统可以提供模板、建议和试算，但不能替双方写死规则；确认后的协议版本及成交时快照才是计算与结算依据。

> **状态说明：**第 1–14 节保留 2026-08-03 首次审计时的真实基线和失败证据，不追改历史结论；整改后的当前状态、验证结果和新证据统一记录在第 15 节。

## 1. 执行结论

当前系统已经具备一条有价值的底层主线：商品可以从真实库存选择后发布；同一批实物可在多个账号扩大曝光而不在上架时占库存；订单成交时再锁定库存；并发下不会把 5 件库存卖成 6 件；取消后预留能够释放。

但它还不能安全承载本次两个现实案例。关键阻断集中在四件事：

1. 不同经营主体之间无法完成定向货盘交接。
2. CNY 成本、JPY 售价和固定发货费缺少统一、强制的换汇与币种语义。
3. 当前合作规则被限制为少数固定佣金模型，不能完整记录“双方实际约定”；本次案例约定按利润分成，但系统中的 50% / 20% 只能按成交额返佣。
4. ItemUnit 身份、跨国选仓和货盘余量可能显示或分配错误。

| 维度 | 评分 | 结论 |
| --- | ---: | --- |
| 可用性 | 2 / 5 | 库存选品、发布和共享锁库可用；采购成本不明确、跨主体授权及完整结算主链被阻断。 |
| 易用性 | 2 / 5 | 新货盘页已明显简化，但“返佣、合作方、代发主体、节点”等概念仍要求用户先懂系统模型。 |
| 数据准确性 | 1 / 5 | 已复现跨币种直接相减、按成交额返佣、ItemUnit 替换、错误选仓和货盘余量陈旧。 |

综合判定：适合继续作为内部原型验证，但不适合在未修复 P0/P1 前用于真实跨币种分账或一物一单交易。

## 3. 标准账号、经营主体与业务关系

```mermaid
flowchart LR
  SA["供应商 A / B / C\n合作方，无登录"] --> JO["首饰货主经营主体\n库存所有者 / 发布方"]
  JO -->|"定向货盘"| MO["我的经营主体\n质检 / 日本发货 / 可代卖"]
  MO -->|"仓库任务授权"| MW["仓库执行员\n不看采购成本"]
  MO -->|"Mercari / Yahoo 上架"| JP["日本渠道账号"]
  JS["日本采购供应商\n合作方，无登录"] --> MO
  MO -->|"毛绒货盘"| RB["朋友 B 独立经营主体\n只看自己的代卖与收益"]
  RB -->|"闲鱼等上架"| CN["国内渠道账号"]
```

正确的身份边界应是：

- 经营主体拥有货盘、库存权益和结算责任。
- 团队成员账号只决定谁能操作，以及能否查看成本。
- 供应商、代卖方、代发方是合作关系，不等于团队登录账号。
- Mercari、Yahoo、闲鱼是销售渠道账号，不等于供应商或经营主体。
- 仓库只是货物所在和执行任务的节点，不拥有货盘。

## 4. 本次案例的金额约定与真值

固定汇率：`1 CNY = 20 JPY`、`1 JPY = 0.05 CNY`。金额保留两位，汇率保留八位。

本节公式只用于复核本次两个案例，不是系统应写死的通用佣金规则。现实合作可以约定固定金额、成交额比例、利润比例、赚取差价、阶梯规则或成交后人工确认；系统应以双方确认的协议为准，只提供计算建议和快捷模板。

```text
可分配净利润 = 成交额
             - 平台费
             - 折算后的采购成本
             - 分摊物流与税费
             - 售后费用
             - 固定发货服务费
```

缺失汇率时必须阻止利润确认和结算。在本次案例的明确约定中，固定发货费作为独立应付行支付给发货方，剩余净利润再按约定比例分成；其他合作可以采用不同费用承担方式和分钱口径。

### 5.3 业务能力缺口

- 采购质检只能对整张采购单做 `PASSED` 或 `FAILED`，不能在同一行中表达“部分通过、部分待复检、部分退供应商”。
- 采购收货建批次时只把 `line.unitPrice` 写入库存成本；`allocatedFee`、国际运费、税费和质检服务费不会自动进入 ItemUnit/批次单位成本。
- 供应商字段是自由文本或无外键的 `supplierId`，无法可靠区分 A/B/C，更无法在同一批多来源商品上追溯。
- 集运页面可以表达起运仓和目的仓，但缺少重量、合箱条件、报关金额、税费和“人肉携带”等业务记录。

### 8.1 跨币种代卖复现

为隔离单一算法问题，专项使用以下输入：

| 项目 | 正确口径 | 系统结果 |
| --- | ---: | ---: |
| 售价 | JPY 5,000 | JPY 5,000 |
| 供货成本 | CNY 100 = JPY 2,000 | 参与计算时直接使用数值 100 |
| 平台费 10% | JPY 500 | JPY 500 |
| 可分利润（暂不含物流和发货费） | JPY 2,500 | 未作为分成基数 |
| 代卖方 50% | JPY 1,250 | JPY 2,500 |
| 系统预计毛利 | 不应在缺少完整费用时确认 | JPY 1,900，即 `5000-100-500-2500` |

| 场景 | 正确行为 | 系统行为 |
| --- | --- | --- |
| 无 GBP→CNY 汇率 | 阻止确认或结算 | `GBP 10000` 返回 `CNY 10000` |
| 仅有 2020 年 EUR→CNY 汇率 | 2026 业务应阻止或明确确认旧汇率 | 直接得到 CNY 700 |
| 同币种 | 原值 | 正常 |
| 不同业务日期 | 取不晚于业务日的最新汇率 | 正常 |

## 10. 四类汇总

### 10.1 无法完成

- 货主定向发布给另一个独立经营主体，并让对方真实账号看到货盘。
- 只知道整批总价时先登记采购、后补或分摊 SKU 成本。
- 同一采购行部分通过、部分待检、部分退供应商。
- 将人肉携带、邮局直邮、集运合箱作为不同物流路径完整登记。
- 按双方已经确认的合作条款结算；本次案例恰好是“扣除约定成本和费用后的利润按 50% / 20% 分成”。

### 10.2 功能过重

- 发布时要求用户同时理解市场可见性、店铺、合作方、代发组织和发货节点。
- “渠道是否可卖”“谁负责发货”“谁能看见”混在同一高级区。
- 用户只想说“给朋友 B 卖、我发货、利润给他 20%”，系统却要求先理解多个主数据模型。

### 10.3 UI 不友好

- 页面先要求选择固定佣金类型，不能先记录“双方到底怎么约定”；“成交价返佣”和本次的“剩余利润分成”又很容易被误认为同一件事。
- 固定发货费旁没有币种，详情页又跟随供货币种显示。
- 采购页没有“总价已知、明细成本稍后分配”的入口。
- 物流页没有按现实语言提供“我带回国 / 集运 / 邮寄”的选择。
- 跨主体授权失败时，代卖方只看到空状态，不知道是未发布、未授权还是关系未建立。

### 10.4 数据错误

- 缺汇率仍继续金额计算。
- 成本和售价跨币种直接相减。
- 系统只能执行固定的成交额返佣等模式，无法准确执行本次已经确认的利润分成约定。
- ItemUnit 被替换。
- 日本订单锁上海货。
- 其他渠道出库后货盘余量仍为旧值。
- 运费、税费和质检费未形成可追溯的到岸成本。
- 不同币种的结算行被原值相加，结算头与行级本位币金额不一致。
- 固定发货费虽已配置，发货后没有费用事件、应付行或执行人收益。

## 11. 建议的简化方案

### 11.1 发布货盘默认只保留五件事

1. 选哪些商品。
2. 我每件至少要收多少钱，以及这个价格的币种。
3. 谁可以卖：公开、指定朋友/经营主体。
4. 谁发货：我发、对方发、指定服务方；固定发货费和币种。
5. 双方怎么约定分钱：先记录约定原文，再由系统建议结构化计算方式。

其余内容放进“高级规则”，并仅在用户选择对应模式后逐步出现。

### 11.2 用生活化表达替换内部模型

| 当前表达 | 建议表达 |
| --- | --- |
| 经营主体 | 这批生意归谁 |
| 合作方可见 | 只给指定朋友/公司看 |
| 代发服务商 | 谁负责打包发货 |
| 指定发货节点 | 通常从哪里发货 |
| 返佣比例 | 你和对方约定怎么分钱 |
| ItemUnit | 一物一单 / 指定这一件 |
| 库存池 | 共享的真实库存 |

### 11.3 库存模型

- “上架曝光数量”和“真实可售数量”必须分开显示。
- Listing 不占库存；订单成交时加锁，这一点保留。
- 货盘余量必须实时由库存、预留、安全库存和可发市场计算，不存成长期快照。
- ItemUnit 订单只允许锁定指定单件；不可用就阻止并提示重新选择，绝不自动换货。
- 发货仓按订单国家、节点能力和 ShippingLane 选择；若无可用路径必须阻止，不用最早入库批次兜底。

### 11.4 成本和分账模型

- 整批采购允许处于“成本待分配”状态，但此状态下禁止确认利润和结算。
- 提供按数量、重量、申报价、手工金额四种分摊方式。
- 采购成本、国际运费、税费、质检费分别保留原币、汇率日期和本位币金额。
- 固定发货费拥有自己的币种和收款方，不跟随供货价或销售价猜测。
- 结算使用双方确认的规则版本和费用行；确认前展示货主、代卖方、发货方各自应收。
- 任一跨币种行缺汇率或汇率过期时，阻止“确认利润/生成结算”。

### 11.5 以双方约定为核心，而不是写死佣金类型

> 补充结论：佣金、分成和费用承担没有一个应被系统写死的“标准答案”。按纯利润、固定金额、成交额比例或赚差价都只是具体合作案例；最终依据必须是双方确认的约定。系统负责提供建议、试算、版本和留痕，不负责替双方决定如何分钱。

- 系统先保存合作条款原文、参与方、生效时间和适用商品，固定金额、成交额比例、利润比例、赚差价、阶梯规则等只是建议模板。
- 系统可以根据条款推荐供货价或计算方式，但必须明确标记为“系统建议”，不能替代双方约定。
- 双方确认后的结构化规则才是订单和结算依据；成交时保存规则快照，后续修改不得改变历史订单。
- 无法完全结构化的特殊合作允许“成交后确认”和人工调整，但必须记录金额、币种、原因、操作人和确认人。
- 费用是否进入计算基础、由谁承担、谁收取以及使用什么币种，都属于合作条款，不应由系统根据字段位置自行猜测。
- “费率”只是一条协议中的可选参数，不应默认等同于佣金率或净利润分成比例；同一协议可以同时包含固定金额、比例、差价、封顶/保底和人工调整。
- 运费、税费、平台费、发货服务费等也不应固定视为“必扣成本”。系统应让双方逐项约定承担方、收款方、币种以及是否进入分成基数。
- 通用计算模型应是 `双方约定的规则（成交额、数量、成本、指定费用等） + 经确认的调整项`，而不是预设一个唯一的“纯利润”公式。

### 11.6 跨角色交接

- Partner 应能明确关联目标 `organizationId`，授权对象是经营主体，不是发布方自己库里的孤立合作方记录。
- 给代卖方一个“朋友发给我的货盘”入口，显示授权来源、可卖商品、供货价和自己的预计收益。
- 给仓库执行员一个任务收件箱，只展示收货、质检、转仓和发货所需字段；采购成本默认隐藏。
- 空状态要区分“没有公开货盘”“尚未建立合作关系”“有货盘但未授权给当前主体”。

## 12. 建议修复顺序

### 第一阶段：金额、库存与身份安全

1. 缺失/过期汇率阻断；所有金额先转换到明确结算币种再计算。
2. 建立可版本化的双方合作条款与结算规则；固定金额、比例、差价、利润分成等只作为模板，固定发货费仍需独立币种和收款方。
3. 禁止 ItemUnit 回退到同 SKU 库存。
4. 按国家和 ShippingLane 选仓，无路径即阻止。
5. 货盘余量改为实时计算，并保留并发锁库。

### 第二阶段：打通现实主流程

1. 修复跨经营主体定向授权和 Partner↔Organization 关系。
2. 支持批次总成本待分配、费用资本化和完整成本追溯。
3. 支持数量级部分质检、待复检和退供应商。

### 15.3 “双方约定优先”的最终产品规则

- 纯利润 50% / 20% 只保留为本报告算例，不是系统默认答案。
- “费率”只是协议中的可选参数，可以与固定金额、差价、保底/封顶和人工调整组合，也可以完全不用费率。
- 运费、税费、平台费、供货成本和发货服务费是否由某方承担、是否进入分成基数、使用什么币种，都由本次协议决定。
- 系统建议必须可修改并明确标注为建议；双方确认的原文、结构化规则版本和成交快照共同形成审计依据。
- 规则无法可靠自动化时必须选择“成交后双方人工确认”，系统不得根据一个百分比自行推断结算。
