## domain.md

### 核心抽象原则
1. SKU ≠ 库存
2. 库存只通过 Lot 或 ItemUnit 表示
3. 所有库存变化必须通过 StockLedger
4. 成本在库存形成时固化，不允许回写
5. 不为单一品类（如盲盒）设计特例
6. 商品组是 SPU-like 的款型容器；规格 SKU / 独立 SKU 才是可交易维度
7. SKU 是商品与账务统计维度；Lot / ItemUnit 是库存与成本承载维度

### 关键领域对象
- 商品组（GROUP）：类似 SPU 的款型/系列容器，例如 `AJ1 芝加哥 2015`、`火影忍者 晓组织系列`、`Nike SB 短袖 2011 小花猫 黑色`。商品组保存共用的品牌、品类、品牌货号/款号、图片、说明和规格维度，但不直接承接库存、采购、上架或销售。
- 规格 SKU（VARIANT）：商品组下的可交易规格，例如 `42码`、`小南`、`10cm`、`M`。用户只需要输入短规格，系统生成完整名称与内部 SKU 编码。
- 独立 SKU（SIMPLE）：没有规格拆分、可以直接采购/入库/上架/销售的商品，例如 `竹筐`。
- InventoryLot：全新商品批次（数量型，数量以 StockLedger 汇总为准）
- ItemUnit：二手/瑕疵/唯一件/需贴标拍照的单件库存（单件型，归属于规格 SKU 或独立 SKU）
- StockLedger：库存流水真相源
- Order / OrderLine：销售订单与行
- Allocation：订单与库存的绑定
- InventorySplit：库存拆分事件（通用）
- RefPrice：参考价格档案（观察值）

### 商品主档 / SPU-like 规则

- 本系统不直接把概念命名为 SPU，但“商品组”在表单和列表使用体验上承担 SPU-like 职责。
- 商品组只回答“这是什么款型/系列”，不回答“这一件/这一批货在哪里”。
- 规格 SKU / 独立 SKU 回答“哪一个具体规格可以被采购、入库、上架和销售”。
- 品牌货号/款号（如 Nike `555088-101`）是外部商品识别号，不等于系统内部 SKU 编码；系统可以用它作为自动编码基础。
- 规格名称应尽量短：用户输入 `42码`、`小南`、`10cm`、`M` 即可，系统展示为 `商品组名称 · 规格名称`。
- 中古/二手成色不是 SKU 层级，除非成色本身就是市场公认的商品规格；默认应记录在 ItemUnit 或商品情报观察记录上。
- 商品主档列表默认按商品组聚合展示，规格 SKU 以 chip、tab、展开行或紧凑子行呈现；业务单据选择器默认只选择规格 SKU / 独立 SKU。

### 设计哲学
- 拆分是事件，不是状态
- 分配先于确认
- 推荐结果必须可解释、可回溯

### SKU / 库存统计口径

- 商品组统计 = 其所有规格 SKU 的库存、上架、采购、销售汇总；商品组本身不直接承载可售库存。
- 规格 SKU / 独立 SKU 统计 = 自身 InventoryLot 数量 + 自身 ItemUnit 件数。
- 批次库存数量 = StockLedger 对 InventoryLot 的汇总，不直接信任 InventoryLot.status。
- 单件库存数量 = ItemUnit.status + Location.isSellableDefault 的聚合视图；ItemUnit 仍然属于 SKU 体系下的库存，不是独立商品主档。
- 上架数量 = 规格 SKU 的 SKU Listing 与 ItemUnit Listing 聚合到商品组；ItemUnit Listing 用于定位具体单件，不改变商品归属。
- 账务维度 = OrderLine.skuId；成本来源由 OrderAllocation 决定，LOT 取批次成本，ITEM_UNIT 取单件成本。
- 展示分组 = 页面层的临时聚合兜底；当历史数据尚未标明商品组，但同品牌/分类/系列或中文命名前缀明显属于同一系列时，档案和批次页可先合并展示。展示分组不改变 SKU.parentSkuId，不作为账务、库存或上架真相源。

### 当前产品主线

当前阶段优先回答五个问题：

1. 货在哪里？
2. 这件货能不能卖？
3. 卖在哪个平台？
4. 下单后能不能按时发？
5. 最后到底赚了多少钱？

本阶段暂不把班车目标重量、截止装箱时间、SKU 缺重量阻断利润计算作为核心约束；这些进入后续集运精细化阶段。
