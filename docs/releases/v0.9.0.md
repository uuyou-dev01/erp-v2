## Security changes

- Production self-signup defaults to disabled.
- Sessions bind to user identity, account state, expiry and session version.
- Password changes, administrative resets and account suspension invalidate old sessions.
- Production startup rejects development identities, demo passwords and missing/default secrets.
- Scheduled FX, notification and retention endpoints require independent secrets.
- Private assets require authenticated, tenant-scoped download authorization.
- Production dependency audit must contain zero critical/high findings.

## Deployment outline

1. Verify the original backup checksum and restore it to `erp_recovery_v090`.
2. Generate and approve the cleanup manifest; apply it transactionally to a clone.
3. Dump the cleaned database and prove it restores into a new PostgreSQL 17 database.
4. Build one immutable image labeled `v0.9.0-<sha>` from the release commit.
5. Deploy UAT, run the complete screenshot matrix and close all P0/P1 findings.
6. Stop UAT and deploy the same image with the cleaned production backup.
7. Verify read-only production smoke checks, then switch DNS.

## Rollback

1. Stop application and scheduler writes.
2. Preserve a diagnostic dump and asset snapshot from the failed release.
3. Restore the pre-release immutable database dump and corresponding asset snapshot.
4. Redeploy the prior immutable image tag; never retag `latest`.
5. Run readiness, login, permission, report and private-asset read-only checks.
6. Record the incident and rollback SHA in this release document and `CHANGELOG.md`.

Database migrations that cannot be safely reversed require forward repair against
a restored copy. Never improvise destructive SQL on the only production database.
