## 1. 实施目标

在不复制 PC ERP 业务逻辑的前提下，交付两条可独立产生价值、最终互相连接的能力：

- **工作流 A：商品与价格采集**
- **工作流 B：移动任务执行**

共同基础包括移动鉴权、设备、附件、审计、通知、幂等和并发控制。

## 2. 排期原则

1. 先证明“移动动作能够安全改变正式业务状态”，再扩展大量动作。
2. 先完成手动采集闭环，再增加 OCR/AI 和系统分享。
3. 先复用现有任务和 Workflow Action，再补新的任务类型。
4. 先站内通知，再启用 Web Push。
5. 正式业务动作必须在线；只有采集草稿允许离线排队。
6. 每个阶段必须有独立验收和可回滚开关。

## 3. 发布版本概览

| 版本 | 目标           | 主线 A：价格/购入               | 主线 B：任务执行                         |
| ---- | -------------- | ------------------------------- | ---------------------------------------- |
| R0   | 领域与安全基础 | Capture 意图、采购桥接合约      | 移动动作策略、幂等、并发                 |
| R1   | 移动执行 MVP   | 手动记录价格入口                | 今天、我的任务、委托、补物流、到货、发货 |
| R2   | 采购采集闭环   | 截图/图片、真实购入、QuickEntry | 分流、入库、凭证、异常                   |
| R3   | 系统分享与通知 | 快捷指令/Share Extension、OCR   | Web Push、深链、角标                     |
| R4   | 智能化与规模化 | 匹配、去重、价格变化            | 批量现场操作、监控与优化                 |

## 12. 建议开发顺序

如果只有一个开发主线，按以下顺序：

1. Phase 0：基线与决策。
2. Phase 1：共享移动基础。
3. Phase 2：任务执行 MVP。
4. Phase 3：手动价格/购入。
5. Phase 4：分流、入库和履约扩展。
6. Phase 5：截图/OCR/分享。
7. Phase 6：Web Push。
8. Phase 7：智能化与批量效率。

这样排序的原因：现有 Task、Notification 和 Workflow Action 已存在，移动任务 MVP 能最快验证“独立执行端”的价值；Capture 的来源模型更复杂，应先跑通手动意图和采购桥接，再增加识别能力。

如果可以双线并行：

- 小组 A：Phase 1 设备/附件/移动 API + Phase 2 任务执行。
- 小组 B：Capture 数据模型 + Phase 3 手动采集。
- 两组共同评审 Observation/QuickEntry/PurchaseOrder 的事务边界和对象存储。

## 13. Definition of Done

每个移动动作完成必须满足：

- [ ] 产品规则和风险等级已记录。
- [ ] 服务端权限校验已覆盖。
- [ ] 幂等与并发冲突已覆盖。
- [ ] 业务状态和 Task 在正确事务边界更新。
- [ ] ActivityLog 已记录。
- [ ] 通知不会阻塞业务事务。
- [ ] 移动成功/失败文案说明真实业务结果。
- [ ] 单元、集成、E2E 和至少一台真机验收通过。
- [ ] 功能有 feature flag 或安全回滚方式。

每个采集入口完成必须满足：

- [ ] 原始证据先于解析结果保存。
- [ ] 幂等与来源去重已覆盖。
- [ ] 金额、币种、数量口径需人工确认。
- [ ] 低置信度不自动建立/合并 SKU。
- [ ] Observation/QuickEntry/采购对象可反查 Capture。
- [ ] AI/OCR 失败时仍能人工完成。

## 14. 发布与回滚

- 按组织和用户启用 feature flag。
- 先内部账号、再单店铺、再多店铺。
- 新 Mobile API 使用版本前缀。
- 新动作可以单独关闭，不影响 PC 原流程。
- 推送发送器可以独立停用，站内通知仍保留。
- 解析器升级只影响新任务；原始 Capture 不覆盖。
- 数据迁移先加可空字段和新表，不立即删除旧路径。
