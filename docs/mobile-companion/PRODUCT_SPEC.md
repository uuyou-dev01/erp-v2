# ERP 随身助手详细产品需求

状态：第一版已实现；R4 智能匹配与批量能力保留为后续路线
最后更新：2026-08-01

## 1. 产品背景

现有 ERP 适合在 PC 上管理完整业务，但移动场景中的工作通常更轻、更即时：

- 在闲鱼、千岛或微信中看到商品，需要马上留下价格或购入记录。
- 商品到货时，需要在现场拍照并确认数量与位置。
- 发货时，需要扫描运单、上传凭证并确认发出。
- 委托其他成员处理后，需要知道对方是否接受、进行中或已完成。
- 收到通知后，希望直接完成对应节点，而不是打开 PC 后再寻找业务单据。

如果只是把 PC ERP 做响应式缩放，仍会保留复杂导航、宽表格、长表单和大量无关信息，无法解决“几秒钟完成一个现场动作”的问题。

因此需要独立的移动执行产品，与 PC ERP 共用业务数据和领域服务，但拥有独立的信息架构和交互。

## 2. 产品定位

### 2.1 产品名称

暂定：`ERP 随身助手`。

### 2.2 核心用户

- 采购人员：记录看到的价格、登记已购入、补物流。
- 收货/仓库人员：确认到货、异常、分流和入库。
- 发货人员：核对商品、扫描运单、上传凭证、确认发货。
- 负责人：委托任务、查看进度、接收异常和完成通知。
- 管理者：查看关键异常和超时事项，但不在手机端进行复杂配置。

### 2.3 产品目标

1. 常见节点在 10–30 秒内完成。
2. 用户不需要理解 PC ERP 的模块结构。
3. 手机动作与正式业务状态严格一致。
4. 每次操作能够追溯到人、设备、时间、证据和原始业务对象。
5. 网络或识别失败时不丢失原始采集内容。
6. 移动端权限不超过当前用户在对应店铺和任务中的权限。

### 2.4 非目标

- 不复制完整 PC ERP。
- 不在第一版维护复杂商品组/SKU 结构。
- 不在第一版提供完整采购单、销售单或库存列表编辑。
- 不提供复杂报表、经营分析和财务配置。
- 不后台读取微信聊天、浏览历史或其他 App 私有数据。
- 不绕过平台登录、验证码或访问限制。
- 不允许 AI 静默改变 SKU、库存、成本或订单状态。

## 3. 整体信息架构

移动端采用四个一级入口。

### 3.1 今天

首页按人的责任和时间排序：

1. 逾期任务。
2. 高优先级异常。
3. 今天到期的我的任务。
4. 新指派、尚未接受的任务。
5. 我委托且发生异常/超时的任务。
6. 最近通知。

首页只显示每项的摘要和主动作，不展示完整业务详情。

### 3.2 待办

固定分段：

- `我的任务`：当前用户需要执行。
- `待领取`：允许当前用户领取的开放任务。
- `我委托的`：当前用户创建或转交给别人的任务。
- `已完成`：最近完成记录，只读。

可使用轻量筛选：今天、逾期、采购/物流、仓库、发货、异常。

### 3.3 采集

固定四个快捷入口：

- `已购买`
- `记录价格`
- `扫物流单`
- `拍照/截图导入`

系统分享入口、快捷指令或后续 Share Extension 最终都进入同一个采集草稿。

### 3.4 我的

- 当前账号与角色。
- 当前店铺/工作地点。
- 默认到货位置。
- 通知订阅设置。
- 已绑定设备与撤销。
- 本地待上传草稿。
- 退出登录。

## 4. 主线 A：商品与价格采集

### 4.1 业务意图必须独立于输入方式

输入方式回答“用户提供了什么”，业务意图回答“用户想做什么”。两者不能用同一个字段表示。

输入方式：

- `SHARE_URL`
- `SHARE_TEXT`
- `SHARE_IMAGE`
- `SCREENSHOT`
- `CAMERA`
- `MANUAL`
- `BARCODE`

业务意图：

- `OBSERVE_PRICE`：只是看到一个价格。
- `RECORD_PURCHASE`：已经实际购买。
- `UNDECIDED`：先保存证据，稍后整理。

### 4.2 场景 A1：记录市场价格

最小流程：

1. 用户从其他 App 分享链接/截图，或打开采集页拍照。
2. 系统立即保存原始 Capture。
3. 系统提取平台、标题、价格、币种、规格和成色候选。
4. 用户确认价格、币种，并选择或暂不选择标准商品/SKU。
5. 系统创建或更新来源商品及快照。
6. 价格变化时创建 `MARKET_SEEN` 观察。

最小必填：

- 金额。
- 币种。
- 观察时间（默认当前时间）。
- 至少一个来源证据：平台、链接、截图、文字或备注。

允许缺失：

- 标准 SKU。
- 卖家身份。
- 完整描述。
- 精确成色。

信息不完整时进入商品情报采集箱，不创建正式 SKU。

### 4.3 场景 A2：登记已经购买

最小流程：

1. 用户选择“已购买”或从分享入口进入后选择该意图。
2. 系统识别商品、规格、数量、商品价、运费、币种、平台、卖家、订单号和日期。
3. 用户必须确认商品/规格、数量、价格口径和币种。
4. 系统保存来源证据。
5. 同一事务创建：
   - `REAL_PURCHASE + PURCHASE` 价格观察；
   - `QuickEntry`；
   - 信息充分时生成或关联采购单/采购明细。
6. 采购进入 `ORDERED` 或待补全状态，不直接进入可售库存。

采购确认页必须明确区分：

- 商品单价与订单总价。
- 商品价与运费。
- 数量。
- 币种。
- 是否新品/中古/瑕疵。
- 已有 SKU、待匹配 SKU 或待 PC 整理。

### 4.4 场景 A3：一张订单包含多个商品

Capture 允许包含多条识别行。用户可以：

- 删除误识别行。
- 修改每行商品、规格、数量和单价。
- 指定所有行属于同一订单。
- 将多次采集追加到一个采购草稿。

自动合并采购单的确定性优先级：

1. 同店铺 + 同平台 + 同外部订单号。
2. 用户明确选择“加入已有采购草稿”。
3. 同店铺 + 同卖家 + 同币种 + 同用户选择的批次键。

不得只凭日期或相似卖家名称自动合并。

### 4.5 场景 A4：微信私人卖家

微信场景经常没有标准订单号或商品链接，允许使用：

- 卖家备注名。
- 聊天/转账截图。
- 用户手填批次名称。
- 付款金额和日期。
- 商品照片。

这类采集默认 `PRIVATE` 或组织内可见，不自动公开到公共商品情报。

### 4.6 场景 A5：截图中无法确定价格口径

如果截图同时出现原价、优惠价、实付、运费或多个商品金额，系统必须展示候选，不得自动选取后直接入账。

用户确认项：

- 本次记录金额是什么：市场标价、成交单价、订单总额或运费。
- 是否含税/含运费。
- 数量。

低置信度字段使用醒目标识，并保留对应图片区域作为证据。

### 4.7 采集状态

- `RECEIVED`：原始内容已安全保存。
- `PROCESSING`：解析、OCR 或规则处理。
- `NEEDS_REVIEW`：必须人工确认字段或商品身份。
- `READY`：可以执行所选业务意图。
- `IMPORTED`：已写入价格观察和/或采购流程。
- `PARTIAL`：部分结果写入，仍有待补内容。
- `DUPLICATE`：确定性重复，没有产生重复业务记录。
- `FAILED`：处理失败，可重试。
- `DISMISSED`：用户忽略。

### 4.8 采集与正式业务对象的边界

- Capture 是输入证据，不是采购单。
- SourceListing 是平台卖家的来源商品，不是标准 SKU。
- Observation 是价格事实，不是库存成本调整。
- QuickEntry 是进入正式流程的桥梁，不是可售库存。
- PurchaseOrder/PurchaseLine 是正式采购记录。
- 到货、分流和入库完成后才创建或增加库存。

## 5. 主线 B：移动任务执行

### 5.1 任务卡片

每张任务卡只显示：

- 动作名称。
- 商品/订单/采购单摘要。
- 当前地点或目标地点。
- 委托人/负责人。
- 截止时间和超时状态。
- 主操作按钮。

次要信息折叠；完整历史和复杂明细通过“在 PC 查看”进入原系统。

### 5.2 任务状态

沿用现有状态：

- `OPEN`
- `ASSIGNED`
- `IN_PROGRESS`
- `DONE`
- `CANCELLED`
- `OVERDUE`

移动端行为：

- 开放任务可以按权限领取。
- 指派给我的任务可以接受/开始。
- 业务动作成功后自动完成任务。
- 不能单独点击“完成”绕过业务动作，除非该任务明确是纯人工 Check。

### 5.3 支持的节点与移动表单

| 节点       | 手机必要字段                  | 证据/扫码                | 完成后的业务结果          |
| ---------- | ----------------------------- | ------------------------ | ------------------------- |
| 补采购物流 | 承运商、目标位置、物流单号    | 扫单号可选               | 采购进入在途/待到货       |
| 确认到货   | 到货位置、完整/部分、到货时间 | 到货照片可选；异常时必填 | 进入待分流                |
| 分流       | 入库、集运或转发目标          | 扫位置码可选             | 创建对应后续节点          |
| 确认入库   | 入库位置、数量                | 扫仓位码可选             | 形成可运营库存            |
| 确认订单   | 库存核对                      | 扫商品码可选             | 进入待发货                |
| 确认发货   | 发货方式、运单号              | 发货凭证图片；扫码推荐   | 扣减/确认库存并进入已发货 |
| 确认妥投   | 确认收到或登记异常            | 无                       | 进入待结算                |
| 登记退货   | 原因、退货单号、退款信息      | 退货照片可选             | 回滚/冻结库存，进入检查   |
| 退货检查   | 通过/不通过、备注、位置       | 照片推荐                 | 回到可售或进入异常        |
| 异常处理   | 处理结果、备注                | 根据异常类型             | 重试、转交或进入完整详情  |

### 5.4 纯 Check 任务

部分任务不直接改变采购、库存或订单状态，例如：

- 核对包装是否完整。
- 检查附件是否齐全。
- 确认某人已经联系卖家。

这类任务必须显式标记 `completionPolicy = TASK_ONLY`，可以直接完成，但仍需要记录执行人和备注。

正式业务节点必须使用 `DOMAIN_ACTION_REQUIRED`。

### 5.5 委托

委托操作只要求：

- 负责人。
- 截止时间（可选但推荐）。
- 备注（可选）。
- 是否立即通知。

委托后：

1. Task 变为 `ASSIGNED`。
2. 被委托人收到站内通知/推送。
3. 被委托人的“我的任务”出现该事项。
4. 委托人的“我委托的”显示进度。
5. 完成或异常时通知委托人。

任务转交必须保留原创建人、历次负责人和时间，不覆盖历史。

### 5.6 通知

需要外部推送的事件：

- 新任务指派。
- 任务即将超时。
- 任务已经逾期。
- 委托任务完成。
- 到货或发货异常。
- 高风险动作失败。

只保留站内通知的事件：

- 普通状态变化。
- 已读业务摘要。
- 无需当前用户行动的同步信息。

通知点击后必须深链到具体移动任务或采集审核页，而不是统一打开工作台首页。

### 5.7 扫码与拍照

扫码支持：

- 物流单号。
- SKU/商品码。
- 仓位码。
- 采购单/订单二维码（后续）。

拍照支持：

- 到货现场。
- 包装/商品核对。
- 发货面单和包裹。
- 退货与瑕疵。

照片必须在业务提交前完成上传；业务记录保存对象存储引用，不保存临时本地路径。

## 6. 共用交互规则

### 6.1 一屏一动作

每个执行页面固定结构：

1. 任务/采集标题。
2. 业务对象摘要。
3. 必须核对的信息。
4. 必填字段。
5. 风险或影响说明。
6. 单一主按钮。

### 6.2 默认值

可以默认：

- 当前日期时间。
- 当前用户最近使用的店铺和位置。
- 从任务上下文确定的订单、采购单和 SKU。
- OCR/扫码得到的候选值。

不能静默默认：

- 币种。
- 多商品订单的数量/单价口径。
- 库存调整数量。
- 退款金额。
- 高风险动作原因。

### 6.3 成功反馈

成功页必须说明实际结果，例如：

```text
已确认发货
订单 SO-001 已进入“已发货”
运单号：SF123456
对应任务已完成
```

不能只显示“保存成功”。

### 6.4 失败反馈

区分：

- 网络失败：保留输入，可重试。
- 数据已变化：刷新任务，提示由谁在何时处理。
- 权限不足：不重复提交，提示联系负责人。
- 业务校验失败：指出缺少字段或当前状态不允许该动作。
- 文件上传失败：不提交依赖该证据的业务动作。

## 7. 权限与风险等级

### 7.1 普通动作

- 开始任务。
- 补物流。
- 确认完整到货。
- 上传凭证。
- 委托任务。

按现有角色和店铺权限执行。

### 7.2 中风险动作

- 部分到货。
- 分流到其他位置。
- 确认入库。
- 确认发货。
- 退货检验放行。

需要确认结果影响，部分动作要求照片或扫码。

### 7.3 高风险动作

- 取消采购或订单。
- 登记退货和退款。
- 库存数量调整。
- 修改成本。
- 完成结算。

要求：

- 二次确认。
- 必填原因。
- 必要时主管权限或审批。
- 完整前后值审计。
- 第一版可仅允许跳转 PC 处理。

## 8. 离线策略

- 价格/购入采集允许先保存本地草稿，网络恢复后上传。
- 图片先进入本地待上传队列，成功后再创建服务端引用。
- 正式状态变更默认必须在线完成。
- 不允许离线确认发货、入库、退款或库存调整后延迟同步，以免产生并发冲突。

## 9. 关键指标

### 9.1 效率

- 从打开任务到提交的中位时间。
- 每类任务平均填写字段数。
- 扫码代替手输物流单号的比例。
- 手机完成任务占可移动任务总数的比例。

### 9.2 质量

- 重复状态提交次数。
- 因识别错误被人工修改的字段比例。
- 采购价格/币种修正率。
- 手机动作失败率。
- 无证据发货或异常到货比例。

### 9.3 协作

- 指派到接受耗时。
- 接受到完成耗时。
- 委托超时率。
- 通知点击后完成任务的转化率。

## 10. 第一版验收标准

1. 手机端拥有独立导航和组件，不显示 PC 侧边栏或宽表格。
2. 用户只能看到有权访问店铺中的任务。
3. “我的任务”和“我委托的”结果准确。
4. 补物流、确认到货、委托和发货能在手机完成。
5. 业务动作成功后对应 Task 自动完成。
6. 重复点击不会重复入库、扣库存或创建采购明细。
7. 状态被其他人更新时，手机提交会被拒绝并提示刷新。
8. 图片上传失败时不能提交需要凭证的动作。
9. 可以手动记录市场价格并保留来源。
10. 可以手动登记已购买，同时生成真实购入价观察和 QuickEntry。
11. 登记已购买不会立即增加可售库存。
12. 所有操作能够在 ActivityLog 中追溯。
